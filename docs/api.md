# API guide

Base URL `/api/v1`. Full contract: `docs/openapi.json` (generated by `npm run openapi:generate`) and Swagger UI at `/docs` when `OPENAPI_ENABLED=true`.

## Live notifications

Every in-app notification carries `level` (`critical` | `important` | `light`) and optional `meta` (`{ kind, id, providerId?, status? }`, with kind one of appointment, diagnostic_order, pharmacy_order, prescription, dispatch, affiliation, application, support_case, review, verification, refund) so the apps can pop important ones up and offer a quick action. Both fields are returned by `GET /portal/notifications` and included in push payloads.

`GET /portal/notifications/stream` is a Server-Sent Events endpoint (normal `Authorization: Bearer` header; the apps use fetch streaming). Events: `notification` with `{ id, templateKey, level, title, body, link, meta, createdAt }`, `read` with `{ ids }` when the user marks notifications read on any device, and a comment heartbeat every 25 s. `?since=<ISO>` replays this user's unread rows created after that instant (max 20) so a reconnect loses nothing. It is backed by a MongoDB change stream (fires after the writing transaction commits, works across API instances); at most 5 open streams per user; clients fall back to polling `?unread=true` if the stream is unavailable.

Platform staff are notified by permission (`notifyUsersWithPermission`): new applications → `providers.verify`, support cases → `support.manage`, refund requests → `finance.refunds.approve`, emergencies nobody can take → `dispatch.manage`, reviews awaiting moderation → `reviews.moderate`.

## Conventions

- **Auth**: `Authorization: Bearer <accessToken>` (15 min). Refresh with `POST /auth/refresh` (rotating refresh token, 30 days). Logout revokes the session immediately.
- **Envelope**: `{ "data": … }`; lists: `{ "data": [...], "page": { "limit", "nextCursor", "hasMore" } }`. Pass `cursor` back to get the next page.
- **Errors**: `{ "error": { "code", "message", "details?", "requestId" } }`. Codes include `VALIDATION_FAILED` 400, `UNAUTHENTICATED` 401, `TOKEN_INVALID` 401, `INVALID_CREDENTIALS` 401, `ACCOUNT_LOCKED` 423, `ACCOUNT_INACTIVE` 403, `FORBIDDEN` 403, `SEPARATION_OF_DUTIES` 403, `NOT_FOUND` 404, `CONFLICT`/`DUPLICATE`/`INVALID_STATE_TRANSITION`/`SLOT_UNAVAILABLE`/`SLOT_BUSY` 409, `PRECONDITION_FAILED`/`IDEMPOTENCY_CONFLICT` 422, `PAYLOAD_TOO_LARGE` 413, `UNSUPPORTED_MEDIA_TYPE` 415, `RATE_LIMITED` 429.
- **Money**: integer minor units (paise) + `currency`. Rates in basis points.
- **Idempotency**: endpoints marked "Idempotency-Key required" need a unique `Idempotency-Key` header (8–80 chars) per logical operation; a retry with the same key replays the original response (`Idempotent-Replayed: true`).
- **Optimistic concurrency**: edits that take `expectedVersion` fail with 409 if the record changed.
- **Dates**: ISO-8601 with offset; date-only fields `YYYY-MM-DD`; schedules in IST minutes-from-midnight.
- **Rate limits**: 600 req/min per IP globally, 20/min on auth endpoints, 60/min on role grants (`RateLimit-*` headers).

## curl walkthrough (synthetic data)

```bash
API=http://localhost:4000/api/v1

# 1. sign in (after admin:bootstrap + password reset)
TOKEN=$(curl -s $API/auth/login -H 'content-type: application/json' \
  -d '{"identifier":"owner@example.com","password":"<passphrase>"}' | jq -r .data.accessToken)
AUTH="Authorization: Bearer $TOKEN"

# 2. register a hospital with an invited owner
curl -s $API/admin/providers -H "$AUTH" -H 'content-type: application/json' -d '{
  "type":"HOSPITAL","legalName":"Tamluk Care Hospital Pvt Ltd","displayName":"Tamluk Care Hospital",
  "contactPhone":"9800000001","owner":{"fullName":"Owner","email":"owner@tamlukcare.example"},
  "facility":{"bedCount":40,"hasEmergency":true},
  "location":{"name":"Main","addressLine1":"Hospital Road","city":"Tamluk","district":"Purba Medinipur",
              "pincode":"721636","latitude":22.30,"longitude":87.92,"regionCode":"WB-PMD-TAMLUK"}}' | jq .data.id

# 3. upload a registration certificate (raw body) and submit for verification
curl -s "$API/admin/providers/$HOSP/documents?documentType=CLINICAL_ESTABLISHMENT_REGISTRATION&fileName=reg.pdf" \
  -H "$AUTH" -H 'content-type: application/pdf' --data-binary @reg.pdf
curl -s -X POST $API/admin/providers/$HOSP/submit -H "$AUTH"

# 4. as a different user with providers.verify: record checks, then approve
curl -s $API/admin/verification-cases/$CASE/checks/FACILITY_REGISTRATION -H "$AUTH2" -H 'content-type: application/json' \
  -d '{"status":"PASSED","method":"MANUAL_DOCUMENT_REVIEW","evidenceDocumentId":"'$DOC'"}'
curl -s $API/admin/verification-cases/$CASE/decision -H "$AUTH2" -H 'content-type: application/json' \
  -d '{"decision":"APPROVE","note":"Registration certificate verified against WB CEA register"}'

# 5. public discovery
curl -s "$API/discovery/search?q=liver%20disease&lat=22.3&lng=87.92&radiusKm=15" | jq '.data.doctors[0], .data.emergency'

# 6. patient books (idempotent)
curl -s $API/patient/appointments -H "Authorization: Bearer $PATIENT_TOKEN" -H 'content-type: application/json' \
  -H "Idempotency-Key: book-$(uuidgen)" -d '{"slotId":"'$SLOT'","patientProfileId":"'$PROFILE'"}'

# 7. create a payment order; the gateway webhook (HMAC-signed) confirms payment
curl -s -X POST $API/patient/transactions/$TXN/payment-order -H "Authorization: Bearer $PATIENT_TOKEN" -H "Idempotency-Key: pay-1"

# 8. finance: draft → submit → (other user) activate a commission policy
curl -s $API/admin/finance/commission-policies -H "$AUTH" -H 'content-type: application/json' -d '{
  "code":"CONSULT_DEFAULT","name":"Consultation default","category":"CONSULTATION","method":"PERCENTAGE",
  "rateBps":1000,"taxRateBps":1800,"effectiveFrom":"2026-11-01T00:00:00+05:30"}'
```

A ready-to-import Postman collection can be generated from `docs/openapi.json` (Postman → Import → OpenAPI 3.1).

## Versioning

Breaking changes go under `/api/v2`; additive changes (new optional fields, new endpoints) ship under `/api/v1`. The OpenAPI document is regenerated in CI so the committed file always matches the code.

## Invoices

Immutable PDF documents (pdfkit, A4, platform logo top-left or the platform name when no PNG/JPEG logo is set). Numbers look like `CV-INV-2026-27-000001`: prefix from `invoice.number_prefix`, kind code (`INV` tax invoice, `CRN` credit note, `COM` commission invoice, `STM` settlement statement), Indian fiscal year (April–March, IST), six-digit sequence allocated atomically per kind per year (`invoice_counters`, one findAndModify). Corrections are credit notes; nothing is edited.

**InvoiceMeta**: `{ id, number, kind, issuedAt, currency, totalMinor, taxMinor, sourceType, sourceId, transactionId, providerId, patientProfileId, pdfUrl }`.

| Route | Auth |
|---|---|
| `GET /invoices/:id` | Patient account holder of the invoice's profile, active provider member with `view_finance` for the invoice's provider, or `finance.read`. 404 unknown, 403 otherwise. |
| `GET /invoices/:id/pdf` | Same. `application/pdf`, `Content-Disposition: attachment; filename="<number>.pdf"`, `Cache-Control: private, no-store`. |
| `GET /patient/invoices?limit&cursor` | Signed-in patient: tax invoices and credit notes of every profile on the account, newest first (standard list envelope `data[]` + `page`). |
| `GET /patient/transactions/:transactionId/invoices` | Account holder of the transaction → `{ items }`. |
| `GET /portal/providers/:providerId/invoices?limit&cursor&kind` | `view_finance` member of that provider or `finance.read`; newest first. |
| `GET /portal/providers/:providerId/transactions/:transactionId/invoices` | Same; the transaction must belong to the provider → `{ items }`. |
| `GET /portal/providers/:providerId/settlements/:batchId/invoices` | Same → `{ items }` (commission invoice + statement; empty until those are generated). |
| `GET /admin/finance/transactions/:transactionId/invoices` | `finance.read` → `{ items }`. |
| `GET /admin/finance/settlements/:batchId/invoices` | `finance.read` → `{ items }`. |
| `GET /admin/finance/invoices/sample.pdf` | `finance.read`. Sample tax invoice with the current `invoice.*` settings and logo; not stored or numbered. |
| `POST /admin/finance/transactions/:transactionId/invoices/regenerate-missing` | `finance.manual.record`, audited → `{ transactions, created }`. |
| `POST /admin/finance/invoices/regenerate-missing` | `finance.manual.record`, audited; backfills every PAID / PARTIALLY_REFUNDED / REFUNDED transaction. |

Generation: a tax invoice when a transaction becomes PAID (gateway webhook or a manual payment received by the platform); a credit note per succeeded refund (webhook or manual record), referencing the original via `supersedesInvoiceId`. Generation runs after the database transaction commits and never fails the payment flow; a failure is logged and fixed by regenerate-missing. Idempotency: partial unique indexes `invoices_one_tax_invoice_per_txn`, `invoices_one_credit_note_per_refund` (refund id in the line snapshot), `invoices_one_per_batch_provider_kind`. Transactions paid at the provider (PAY_AT_PROVIDER) get no platform invoice.
